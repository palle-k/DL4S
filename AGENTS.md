# AGENTS.md
Guidance for coding agents that work in this repository.

## What this is
DL4S is a pure Swift deep learning library with built-in reverse-mode automatic differentiation (dynamic compute graphs, no special toolchain). It provides tensor operations, NN layers, optimizers, losses, and reference architectures (ResNet18, VGG, AlexNet, Transformer). It supports macOS, iOS, tvOS, watchOS, and Linux.

## Commands
```bash
swift build                                          # build
swift test                                           # run all tests
swift test --filter GradientTests                    # run one test suite
swift test --filter GradientTests/testMatMul         # run one test function
DL4S_LONG_TESTS=1 swift test                         # include the long training runs
swift test --filter Concurrency                      # run the thread-safety stress suite
swift test --filter GPUTests                         # run the GPU suites (skipped without a Metal device)
swift test --sanitize=thread --filter Concurrency    # run it under thread sanitizer
swift test --traits MKL --filter VecTests            # x86_64 Linux with oneAPI: run the MKL smoke test
swift package -Xswiftc -DDL4S_SKIP_MKL_PLATFORM_CHECK generate-documentation --target DL4S   # build the DocC documentation
swift package plugin --allow-writing-to-package-directory swiftformat               # format the code (SwiftFormat, .swiftformat)
swift package plugin --allow-writing-to-package-directory swiftformat --lint        # check the formatting
swift package plugin --allow-writing-to-package-directory swiftlint lint --strict   # lint the code (SwiftLint, .swiftlint.yml)
```

SwiftFormat (`.swiftformat`) formats the code and SwiftLint (`.swiftlint.yml`) lints it. CI is a GitHub Actions workflow (`.github/workflows/ci.yml`) that runs `swift test` in debug and release configuration (`-c release -Xswiftc -enable-testing`) on macOS and Ubuntu, runs the concurrency suite under the thread sanitizer, and runs the two plugin checks on Ubuntu. A second workflow (`.github/workflows/tsan-full.yml`) runs the full test suite under the thread sanitizer on every push to master and on manual dispatch. Both sanitizer jobs run on macOS only: on Linux, TSan does not see `Synchronization.Mutex` and reports every access under the lock as a race (verified with Swift 6.1 and 6.3.3).

On x86_64 Linux, acceleration comes from Intel oneAPI MKL/IPP instead of Accelerate through the `MKL` package trait (off by default): `source /opt/intel/oneapi/setvars.sh`, `export CPATH=${IPPROOT}/include:${CPATH}`, then `swift build -c release --traits MKL` (see README for setup). The trait defines `MKL_ENABLE` for the `DL4S` and `DL4STests` targets. Without MKL or Accelerate, an unoptimized generic fallback is used. A third workflow (`.github/workflows/mkl-integration.yml`) runs `swift test --traits MKL --filter VecTests` on ubuntu-24.04 with oneAPI from the Intel apt repository; it runs on pull requests and pushes to master that touch the CPU backend, `Sources/CMKL`, or `Package.swift`, and on manual dispatch. A fourth workflow (`.github/workflows/docs.yml`) builds the DocC documentation with the plugin flag from the Commands block on every push to master and on manual dispatch, and publishes it to GitHub Pages with the Pages deployment actions. 

Allocation tracing is a debugging aid that is compiled in only with `-Xswiftc -DDL4S_TRACE_ALLOCATIONS`. With the flag, `CPUMemoryOperators.setAllocationTracing(true)` records the call stack of every allocation and prints the call stack of a buffer that is not freed after 5 seconds. Builds without the flag contain no tracing code. Run the tracing test with `swift test --sanitize=thread -Xswiftc -DDL4S_TRACE_ALLOCATIONS --filter Concurrency`.

Tests use Swift Testing (`@Suite` structs with `@Test` functions) in `Tests/DL4STests`. Tests that train real models for minutes (`ModelTests`, `TransformerTests`, and the full-set runs in `MNISTTests` and `TransformerMNISTTests`) have the `.longRunning` trait from `TestUtil.swift`, which skips them unless the `DL4S_LONG_TESTS` environment variable is set, and run `.serialized`. Run them locally with `DL4S_LONG_TESTS=1 swift test`. The short MNIST training runs in `MNISTTests` carry the `.trainsModel` trait: they run with an accelerated backend, in release builds, or with `DL4S_LONG_TESTS` set, because the generic fallback in a debug build needs more than an hour for them. The MNIST idx files in the test directory are bundled as test resources; `MNIST.sample` (5,000 training images) and `MNIST.full` in `MNIST.swift` load them once per process. `TestUtil.swift` also has `expectEqual(_:_:accuracy:)`, `expectClose(_:_:tolerance:)` for tensors, and `numericalGradient(of:at:)` for finite-difference gradient checks.

`ConcurrencyTests` runs inference, backpropagation, dropout, and weight initialization from several raw threads at the same time. It is the acceptance test for the thread-safety work. Run the suite under the thread sanitizer to see data races as reports. `GPUConcurrencyTests` does the same on the GPU, and `--filter Concurrency` runs it too.

The GPU suites (`GPUEngineTests`, `GPUFusedOperationTests`, `GPUConcurrencyTests`, `GPUMemoryTests`) are nested in the serialized suite `GPUTests` (`GPUTestUtil.swift`), because they change global settings of the GPU, such as `GPU.hostExecutionLimit`. They are skipped when the system has no Metal device. `GPUTest.compare` runs an operation on the CPU and on the GPU, once with all operations on the GPU and once with small operations on the host, and compares the results.

## Architecture
Three targets: `CMKL` (a system library target: `module.modulemap` plus `shim.h`, which includes `mkl.h` and `ipp.h`; the MKL include path and link line come from the `mkl-dynamic-lp64-gomp` pkg-config file, the IPP libraries from `link` directives in the module map), `DL4SMacros` (the compiler plugin with the `@Layer` and `@Frozen` macros), and `DL4S`, which depends on `DL4SMacros`, and on `CMKL` only when the `MKL` trait is on. `Package.swift` declares `CMKL` only on x86_64 Linux hosts, so builds on other hosts do not look for the pkg-config file. Accelerate needs no configuration.

### Generic core: Tensor over Element and Device
Everything is generic over two parameters: `Tensor<Element: NumericType, Device: DeviceType>` (`Sources/DL4S/Tensor/Tensor.swift`). Valid elements are `Float`, `Double`, and `Int32` (`Sources/DL4S/Numerics/`).
- `DeviceType` (`Sources/DL4S/Engine/Engine.swift`) bundles three associated types: `Memory: MemoryOperatorsType` (raw allocation, slicing), `Engine: EngineType` (the full kernel catalogue: broadcast ops, gemm, conv, reductions, scatter/gather, etc.), and `FusedOperations: FusedOperationsType` (high-level operations and their first derivatives, see Fused operations).
- `CPU` (`Engine/CPU/`) and `GPU` (`Engine/GPU/`, see GPU device) are the devices. `CPUEngine` methods are thin shims that forward to static methods on the element type (`CPUNumeric` protocol). Loops over the indices of a shape use `StridedIteration` (`Util.swift`), which keeps running offsets in two layouts. Do not use `iterate` or `flatIterate` in kernels: they allocate an index array for every element. The per-type implementations in `Engine/CPU/Numeric/` select between three variants with conditional compilation: `#if MKL_ENABLE`, `#elseif canImport(Accelerate)`, and a generic Swift fallback (`CPUGeneric.swift`).
- Kernels that accumulate into an existing gradient have fused `...Add` variants (`permuteAxesAdd`, `subscriptWriteAdd`, `reverseAdd`, ...). Backward passes use these to avoid a separate add kernel.
- `Tensor` wraps a `TensorHandle` class with copy-on-write (`ensureOwnership()`); views share the parent buffer, and only the root handle frees it.

### Automatic differentiation
Autograd is closure-based and lives in `Sources/DL4S/Tensor/`:
- Each differentiable operation (all in `Tensor/Operators/*.swift`) computes its forward result through the engine, then attaches a `TensorContext` (`Context.swift`) that holds the source tensors and the backpropagation closures. The context has two forms: one closure per source (the default), or one closure for all sources (`backpropagateAll:`) that owns the accumulators and returns every source gradient at once. Use the second form when one kernel produces all source gradients, as `stack` does, so the kernel runs once per backward visit and the closures share no state. Capture only happens when an operand `requiresGradient`.
- `tensor.gradients(of:retainBackwardsGraph:)` (`Tensor.swift`) topologically sorts the graph by `backpropID` and walks it backwards. Backward closures are written with normal tensor operations, so the backward pass builds its own graph when `retainBackwardsGraph: true`, which enables second and higher derivatives. With `false`, accumulated gradients are detached.
- New tensor operation checklist: add the primitive to `EngineType`, implement it in `CPUEngine` (usually delegating to a `CPUNumeric` static, implemented in `CPUFloat`/`CPUDouble`/`CPUInt32`/`CPUGeneric`), then add the public `Tensor` method in the matching `Tensor/Operators/*.swift` file with its `TensorContext` gradient closures. Add a gradient check to `Tests/DL4STests/GradientTests.swift` and tick the README feature list. A high-level operation that an engine can compute in one kernel gets a fused requirement pair instead of a primitive, see the next section.
- Backward closures must not capture the result tensor directly (retain cycle). See `exp`/`tanh` in `Unary.swift`: they capture a copy and recompute the forward value when the backward graph itself needs gradients.
- Debug-only graph tooling: `Tensor.tag`, `OperationGroup.capture(named:)`, and `tensor.graph()` (Graphviz DOT output) are compiled only in `#if DEBUG`. The operation stack that `capture` records is a `@TaskLocal`, so each thread or task has its own stack.
- Each tensor gets its `backpropID` from a process-wide atomic counter (`UniqueID`). Copies keep the id. `ensureOwnership` creates a new tensor with a new id when the buffer is shared.

### Fused operations
A device has two layers of operations. The basic operations of `EngineType` (`vAdd`, `gemm`, `img2col`, ...) read and write buffers, and every engine implements them as kernels. The fused operations of `FusedOperationsType` (`Engine/Fused/FusedOperations.swift`: `convolution2d`, `layerNormalization`, `gelu`, `categoricalCrossEntropy`, `multiHeadAttention`, ...) take and return tensors and compute a high-level operation or its first derivative in one requirement. Their default implementations are in `Engine/Fused/` and compose the result from tensor operations on detached inputs. `DefaultFusedOperations<Device>` uses the default of every requirement, so a device can call it for inputs that its own kernels do not support.
- Every fused operation is a `static func` requirement of `FusedOperationsType` with a default implementation in `extension FusedOperationsType`, never a plain extension method. Generic code calls `Device.FusedOperations`, and only requirements dispatch to the implementation of the device. A constrained extension overload is resolved at the call site and is never called from code that is generic over `Device`.
- The results of fused requirements have no context. A backward requirement (`...Backward`) takes the accumulated gradients of its sources as its last argument (`accumulating:`, an `inout` optional tensor, tuple, or gradient struct). It adds the gradient of every source that requires a gradient to its accumulated gradient, or stores it when the value is nil, and does not change the values of the other sources. It reads `requiresGradient` of its arguments to decide. A weight that is used in many steps, such as a recurrent weight, then gets its gradient added in place by the kernel (`gemm` with beta 1), with no temporary tensor and no separate add. `Tensor.accumulate(_:into:)` adds a computed gradient, and `Tensor.accumulateProduct` adds a matrix product with `gemm` (both in `Context.swift` and `Matrix.swift`). A CPU kernel writes into the accumulated gradient with `CPUKernels.GradientTarget`, which gives a pointer and the beta for the first write, and falls back to a new tensor when the accumulated gradient has a graph or another shape. In-place writes need a uniquely referenced accumulator, so move accumulators with `take()` instead of copying them; a shared buffer is copied before the write. It never takes the forward result, except for operations whose derivative is cheapest to compute from the result (`tanhBackward`, `sigmoidBackward`, `softmaxBackward`, `logSoftmaxBackward`). The backward pass computes intermediates again from the sources. The forward pass does not keep them alive. Side outputs, such as the dropout mask, are part of the result tuple.
- The public tensor operation calls the forward requirement and attaches the context with `attachingContext(tag:sources:backpropagate:)` (`Context.swift`), which uses the `backpropagateAll` form and gives the closure the accumulated gradients of the sources as an `inout` array. The closure calls the backward requirement when the incoming gradient does not require a gradient, which is the case in training. When it does (`retainBackwardsGraph: true`), the closure calls the composed gradient in `Composed` (`Engine/Fused/`) with the tensors of the graph, so autograd derives the second and higher derivatives. The default implementations call the same `Composed` functions with detached tensors.
- `CPUFusedOperations` has kernels in `Engine/CPU/Fused/` for the activations, softmax and log softmax (last axis), layer and batch normalization, convolution, transposed convolution and pooling, scaled dot product attention, dropout, the Adam step, and the step of a gated recurrent unit. Multi-head attention uses its default, which calls the attention kernels. The kernels are Swift, generic over the element type with `@_specialize` for `Float` and `Double`. They work on blocks of `CPUKernels.blockSize` elements or on rows, call the accelerated primitives of `CPUNumeric` for transcendental functions, reductions, `gemm`, and `img2col`, and use element-wise loops for the rest. Write these loops so that the compiler vectorizes them: offset the pointers once per block and index with the loop variable only (checked `offset + i` arithmetic prevents vectorization), and load every operand before a comparison (`x[i] > 0 ? g[i] : 0` becomes a branch). The loops are slow in debug builds, so training runs in debug builds are slower than with the defaults. Convolutions process the batch in chunks, so their window matrix has at most `CPUKernels.maximumColumnElements` elements.
- Two requirements are not tensor operations with a context. `adamUpdate` updates the moments of one parameter in place and returns the new parameter; `Adam` calls it when its hyperparameters are scalars. `gatedRecurrentUnitStep` computes one time step of `GRU`. The layer keeps its loop over the time steps, and autograd connects the steps, so no requirement covers a whole sequence.
- `FusedOperationTests` checks every fused operation against a reference composed from basic operations, and checks the first and second derivatives against central differences. `CPUFusedKernelTests` compares every CPU kernel with `DefaultFusedOperations<CPU>` on shapes that cross block and chunk boundaries, with empty and with prefilled accumulated gradients. Add a case to both for a new fused operation or kernel. `GPUFusedOperationTests` compares the GPU kernels with the CPU through the public tensor operations, including the gradients.

### GPU device
`GPU` (`Engine/GPU/`, compiled with `#if canImport(Metal) && canImport(MetalPerformanceShaders)`) runs on the system default Metal device. `GPU.isAvailable` tells whether one exists; the creation of a GPU tensor without one traps.
- Memory: `GPUMemoryOperators` stores tensors in `MTLBuffer`s with shared storage, so the host reads and writes them in place. `GPUBuffer` (the `RawBuffer`) is a region of a `GPUStorage`, and views share the storage with an offset. Released storages return their buffers to a pool with size classes (`GPUContext.makeBuffer`), and `GPU.clearCache()` empties it. The pool reuses a buffer that the GPU still uses, because the queue runs the command buffers in order. A request takes a pooled buffer of up to twice its size, and a full pool releases its oldest buffers, so that shapes that change in every step, such as padded batches, do not fill it with buffers of unused sizes.
- Autorelease pools: every call into Metal runs in a local `autoreleasepool` (`GPUContext`, `GPUBuffer.hostMemory`, the kernel and graph caches). Metal autoreleases command buffers, encoders, and objects of Metal Performance Shaders, and `MTLBuffer.contents()` autoreleases the buffer. A thread without a run loop, such as the main thread of a command line tool, never drains its pool, so a call without a local pool keeps the buffers alive for the life of the thread. `GPUMemoryTests` trains on such a thread and checks that the allocated GPU memory outside the pool does not grow.
- Execution (`GPUContext.swift`): operations record commands into one command buffer with one serial compute encoder, under a lock, so several threads can record work. The context commits the command buffer after `commandsPerCommandBuffer` commands, and the host does not wait. Every command buffer has a sequence number, and a storage records the sequence numbers of the last command buffers that use and write it. A host access waits only for these (`waitUntilReadable`, `waitUntilWritable`, used by `elements`, `item`, and the CPU fallbacks). `completed` advances over a contiguous run of completed command buffers only, because neighboring command buffers can complete out of order. A storage that no command used yet (`isFresh`) does not wait for a host write: it takes a buffer that the GPU no longer uses. Host data of up to 4 KB goes into the command itself (`GPUKernels.write`). `GPUContext.statistics` counts commands, commits, and host waits; a training step should wait once, when it reads the loss.
- Placement (`GPUPlacement`, `GPUFused.runsKernel`): an operation runs on the CPU implementation, on the shared memory, for element types without GPU kernels (`Double`, and `Int32` for most arithmetic), and for operations with at most `GPU.hostExecutionLimit` elements whose operands are available on the host without a wait. Everything else runs on the GPU. Do not change the placement of an operation based on data values: it must only depend on shapes, types, and the state of the storages.
- Kernels: Metal Shading Language files in `Engine/GPU/Shaders/`, which `Package.swift` copies into the resource bundle as source (`.copy`). `GPUKernelLibrary` loads a group from `Bundle.module` with `prelude.metal` in front of it and compiles it at the first use, so the package needs no Metal compiler at build time. A new group gets a `.metal` file and an entry in `GPUShaderSource.all`, and a test compiles all groups. Element-wise and copy kernels process one element per thread; kernels that only move data work on 32-bit words. Strided copies (`GPULayout`, up to 8 axes after merging) implement permutations, subscripts, stacking, and reversal. Reductions view the tensor as [outer, length, inner] and split long axes into segments. Kernels that contain arrays of SIMD group matrices must unroll their loops over them (`UNROLL`), or the matrices are placed in memory and the kernel is five times slower.
- Matrix products (`GPUMatrixMultiplication`): a SIMD group matrix kernel with 64 x 64 or 32 x 32 tiles, specialized for the transpositions, with split-K for products with few tiles and a long inner axis, and a vector-matrix kernel for one row. Products with at least 2^31 multiplications use `MPSMatrixMultiplication`, which costs about 15 µs of host time per product. `EngineType.gemmBatched` computes a batch with constant strides in one command; its default implementation calls `gemm` for every matrix. Devices without SIMD group matrices (`supportsFamily(.apple7)` is false) use Metal Performance Shaders for all products.
- Fused operations (`Engine/GPU/Fused/`): kernels for the activations, dropout, softmax and log softmax (last axis), layer and batch normalization, the Adam step, and the step of a gated recurrent unit. Convolutions run as Metal Performance Shaders graphs (`GPUGraphs.swift`), compiled once per shape and encoded into the same command buffer. `GPUGradientTarget` lets a backward kernel add to the accumulated gradient in place. The other operations use the default implementations, which run on the GPU through `GPUEngine`.
- `Tensor(_:)` with a tensor of another device, and `copied(to:)`, copy tensors between devices. The copy is not part of the compute graph.

### NN layer system
- `TensorContainer` (`NN/Layer/TensorContainer.swift`) is the traversal protocol: `Parameter`/`Device` types, `visitTensors`, and `adoptLayout(_:)` (default: no-op), which lets a container create tensors or sublayers from a `TensorLayout` (paths and shapes) before a load. `LayerType` and `Optimizer` refine it.
- `LayerType` (`NN/Layer/Layer.swift`) has associated `Inputs`/`Outputs` types (not fixed to tensors, which is how RNNs return tuples), `Parameter`/`Device` types, `callAsFunction`, and one traversal requirement: `mutating func visitTensors(_ visitor: inout TensorVisitor<Parameter, Device>)`. A layer reports every stored tensor with `visitor.weight(&tensor, named:)` or `visitor.frozen(&tensor, named:)` (saved, never trained) and every stored layer with `visitor.sublayer(&layer, named:)` (plain, optional, or array). `parameters`, `weightPaths`, `update`, `freeze`, `unfreeze`, `modifyLayers(of:)`, and `layers(of:)` are extension methods built on the traversal.
- `TensorVisitor` (`NN/Layer/TensorVisitor.swift`) owns the `TensorPath` of the current tensor (property names and positions, rendered as `encoder.blocks.3.Wq` or `0.weights`) and the per-sequence counters. The path is the key of the tensor in checkpoint files.
- The `@Layer` macro (declared in `NN/Layer/LayerMacros.swift`, implemented in the `DL4SMacros` target with swift-syntax) adds the `LayerType` conformance and generates `visitTensors` with one `visitor.stored(&self.x, named: "x")` call per stored `var`. The `stored` overloads on `TensorVisitor` select the role by type, so the macro needs no type information. The generated method uses the type names `Element` and `Device`, which the struct must have as generic parameters or typealiases. `@Frozen` marks a stored property as frozen. `let` tensors are not visited. Layers that decide a role at run time (`Swish`) implement `visitTensors` by hand. Expansion tests live in `Tests/DL4SMacrosTests`.
- Layers are value types and stay the single source of truth. Training code calls `model(input)`, then `model.update { parameters in optimizer.update(&parameters, along: loss.gradients(of: parameters)) }`. The closure receives the weights that require a gradient as an array in traversal order, and the visitor writes them back detached from the graph.
- Optimizers (`NN/Optimizer/`) are values that do not know the model. State is created on the first step from the parameter shapes, checked by count and shape on every step (a mismatch traps), and matched by position; call `reset()` after `freeze()`/`unfreeze()`. Optimizers are `TensorContainer`s: they report their state arrays with `visitor.frozen(&array, named:)` (keys such as `firstMoments.3`) and recreate them from a layout in `adoptLayout(_:)`. Hyperparameters are not state and are not saved.
- `Sequential<First, each Middle, Last>` (`NN/Layer/Sequential.swift`) allows an arbitrary sequence of layers with arbitrary intermediate results to be expressed using result builders.
- Reference architectures live in `NN/Models/`.

### Checkpoints
`NN/Serialization/` reads and writes safetensors files on top of the tensor traversal. The file key of a tensor is its `TensorPath` (or the result of the `naming` closure in the options), and every visited tensor is written, weights and frozen tensors alike. `SafetensorsEncoder` serializes containers to disk. With `sharding`, it writes a directory with shard files and `model.safetensors.index.json` (Hugging Face layout). `SafetensorsDecoder.load(into:from:)` sets weights of an initialized model: it reads all headers, builds a `TensorLayout` from them (empty when a custom `naming` closure is set), lets a copy of the container adopt the layout and checks it against the files, then lets the container adopt the layout, takes the tensors out of the model, maps one shard at a time with `mmap` (`MappedFile.swift`), and copies the entries in file order into the existing buffers, with element conversion. The model is reverted when an error is thrown.

## Conventions
- Every file starts with the MIT license header (`// <Filename>.swift / DL4S / Created by ... / Copyright ...`). New files get the same header.
- Public APIs carry `///` doc comments with `- Parameters:` / `- Returns:`. The reference documentation is DocC output published from CI.
- The package builds in Swift 6 language mode (`swiftLanguageModes: [.v6]` in `Package.swift`), so concurrency diagnostics are errors.
- Layers use `@Layer` and store their tensors as `var` properties named after the paper or the role (`weights`, `bias`, `Wq`). The property name is the tensor path in checkpoints, so do not rename them without a reason.
- Hot generic functions use `@inline(__always)` and `@_specialize(where Element == Float, Device == CPU)`.
- Engine primitives use terse names (`vAdd`, `vsMul`, `gemm`, `img2col`); public tensor methods are spelled out (`matrixMultiplied(with:)`, `permuted(to:)`, `reduceSum(along:)`).

## Debugging
`util/debugger_support/tensor.py` is an LLDB script that adds readable summaries for `Tensor` and `ShapedBuffer` values. Load it with `command script import` in LLDB or from `~/.lldbinit`.

## Documentation & Communication
- All communication, comments, documentation, etc. must use ASD-STE100 Simple Technical English.
- Documentation must follow the Google Developer Documentation style guide. This includes spelling, terminology, choice of words, inclusive language, phrasing and  sentence construction.
- Avoid em-dashes and en-dashes in sentence constructions. Write concisely. 
- Phrases to avoid: "load-bearing", "gated", "the X is real", "X is doing a lot of work", "it's not X, it's Y", "genuinely", "{Ticket}/{fix} lands" / "{fix} has landed"
- Do not include ticket IDs or phases in any code, including unit tests.
- Avoid mannered prose: writing that uses metaphor or a striking phrase where a plain statement would do. Examples: "a dial worth turning" for "a parameter worth varying"; "this point earns its keep" for "this point still matters." Such phrases draw attention to the writing rather than the idea, and they are less precise, because a metaphor carries associations the writer did not intend. When a literal phrase is available, use it.
